## Area 1: Worker Parallelism & Distiller Core

### Architecture Concerns (things that will cause pain)

- **Worker pool is breaking all distiller tests.** All 17 tests that exercise `Distiller` via `distill()` time out at 5s. The Piscina worker references `process-file.worker.js` but this is a `.ts` file — in the Bun test runner, the compiled `.js` may not exist or the worker thread may not resolve correctly. The default `workers: 4` means **every test instantiation** tries to spin up a Piscina pool, which hangs indefinitely. (`src/core/distiller/index.ts:42-51`, `src/core/distiller/index.ts:62`)

- **Worker re-initializes entire language registry per invocation.** `process-file.worker.ts:28-29` calls `getLanguageRegistry()` + `registry.initializeAll()` on **every single file**. Since `getLanguageRegistry()` returns the module-level singleton that auto-initializes on import (`src/core/languages/index.ts:35`), this is double-initializing. But worse, in a worker thread each import is fresh — so every file processed spins up new `TsMorphProcessor` + `Project()` instances. This negates the parallelism gains.

- **Duplicated `mapExportKind` and API conversion logic.** The exact same ~60 lines mapping `ProcessResult` to `ExtractedAPI` format exists in both `distiller/index.ts:299-327` and `process-file.worker.ts:47-70`. When these drift, the sequential and parallel paths will produce different output. (`src/core/distiller/index.ts:513-533` vs `process-file.worker.ts:92-111`)

- **`cumulativeDistilledSize` tracks wrong metric.** At `index.ts:355`, `cumulativeDistilledSize += file.content.length` adds the **original** file content length for files that succeeded, not the distilled size. This makes the progress bar's size ratio meaningless.

- **Worker pool never cleaned up on `distillSelectedFiles`.** Only `distill()` calls `cleanup()` in its `finally` block (`index.ts:115-117`). If `distillSelectedFiles()` is called directly (e.g., from the distill command for pre-selected files), the worker pool leaks — threads stay alive until process exit.

### Pattern Smells (things that suggest structural issues)

- **Silent fallback cascade.** `TypeScriptProcessor` silently catches `TsMorphProcessor` init failure, then `TypeScriptASTProcessor` init failure, then falls back to line-based parsing — all without reporting which path was taken. In production, you could be running the weakest parser on every file and never know.

- **Misleading method name.** `compressFile()` doesn't compress — it reads a file and hashes it. The JSDoc acknowledges this (`index.ts:161`), which means the name is known to be wrong.

### What's Actually Good

- Clean separation between file discovery (`getFilesToProcess`) and processing (`distillFiles`)
- The `finally { cleanup() }` pattern in `distill()` is correct
- Worker architecture direction is sound — just needs the initialization fixed

## Area 2: Language Processing Pipeline

### Architecture Concerns (things that will cause pain)

- **Unused import `PrivateIdentifier` from `ts-morph` in types.** `src/core/languages/types.ts:6` imports `PrivateIdentifier` from `ts-morph` but never uses it. This creates an unnecessary dependency on `ts-morph` for any module importing language types, which includes the worker.

- **Three separate `matchesPattern` implementations.** `TsMorphProcessor`, `TypeScriptASTProcessor`, and `PythonProcessor` each implement their own glob-to-regex pattern matching with subtle differences:
  - `TsMorphProcessor` (`ts-morph-processor.ts:665-677`): escapes `[.+^${}()|[\]\\]` then replaces `*` and `?`
  - `TypeScriptASTProcessor` (`ast-processor.ts:459-466`): only replaces `*` and `?`, no proper escaping
  - `PythonProcessor` (`processor.ts:538-561`): character-by-character escaping of `^+${}()|[]\`

  The AST processor version is **buggy** — a pattern like `test.class` would match `testXclass` because `.` is not escaped.

- **`shouldIncludeExport` in Python processor has redundant logic.** `processor.ts:434-471` checks `node.visibility === "private"` twice with different logic — first with a special-method exception (lines 439-448), then unconditionally (lines 451-452). The second check makes the first one unreachable for the `!isSpecial` case.

- **`filterExports` in Python processor mutates the input array.** `processor.ts:514-536` assigns `const filtered = exports` (reference copy, not clone), then calls `filtered.sort()` — this mutates the caller's array. Should be `[...exports]`.

- **Stale debug comment in AST processor.** `ast-processor.ts:32` has `// hi` — looks like leftover debug. This was also in the staged changes, so it's about to be committed.

### Pattern Smells (things that suggest structural issues)

- **Three TypeScript processors stacked.** `TsMorphProcessor` > `TypeScriptASTProcessor` > line-based fallback. Each has its own member extraction, pattern matching, and filtering logic. The charter says "Pluggable Parsing" with a unified interface — but within a single language you have three parsers with three different behavior profiles.

- **`any` everywhere in TsMorphProcessor.** Parameters typed as `any` (`ts-morph-processor.ts:224, 267, 305, etc.`) despite ts-morph providing real types. This undermines the "strict mode" requirement from the charter.

### What's Actually Good

- `LanguageModule` interface is clean and well-typed
- `LanguageRegistry` is simple and does exactly what it should
- `ProcessResult` / `ExportNode` / `ImportNode` types are well-structured
- Registry tests are passing and cover the key scenarios

## Area 3: File Scanning & Utilities

### Architecture Concerns (things that will cause pain)

- **Two separate glob matching implementations.** `FileScanner.matchesPatterns` (file-scanner.ts:230-283) does manual regex conversion, while `Distiller.getFilesToProcess` (distiller/index.ts:479) uses `globby`. These will behave differently for edge-case patterns. The file scanner's pattern matching is also used against `.gitignore` patterns, which have different semantics than glob patterns (negation with `!`, implicit `**/` prefix for patterns without `/`).

- **`processInParallel` has a broken concurrency limiter.** `file-scanner.ts:574-592`: After `Promise.race(executing)`, it tries to filter completed promises by racing each against `Promise.resolve()`. This doesn't work — a fulfilled promise always wins `Promise.race` against another fulfilled promise. The `stillExecuting` array will always be empty after the catch-based filter, so the concurrency limit effectively resets to 0 each cycle, making it behave like `Promise.all` in batches.

- **`isTextFile` reads every unknown file.** `file-scanner.ts:285-391` reads 1KB of every file without a recognized extension to detect binary content. For large repos with many extension-less files, this adds significant I/O. The file content is then read again later for processing.

### Pattern Smells (things that suggest structural issues)

- **`formatEstimatedTokens` called with byte count.** In `combine/index.ts:225-229`, `formatEstimatedTokens()` is called with `allFiles.reduce((total, file) => total + statSync(file).size, 0)` — this passes **file sizes in bytes**, not token counts, to a function that formats as "~Nk tokens". The resulting output is wrong.

- **Unused `scanParallel` method.** `FileScanner.scanParallel()` exists but appears to never be called. It duplicates most of `scan()` with a different parallelism approach.

### What's Actually Good

- The `default-excludes.ts` pattern categorization is clean and well-organized
- Context-aware exclude functions (`getDistillExcludes`, `getCombineExcludes`) are a nice API
- The `tokens.ts` module is simple and correct
- The uncommitted fix to `countTokens` (adding `allowedSpecial: 'all'`) is appropriate
